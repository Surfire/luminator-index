# 共享索引与首段查询实测

2026-10-13，Apple M5 Max / 128 GB / macOS 27.0.1。
基线为上一轮已安装版本 `d1939b9`，Tinycast 保持 `d2656a1` 的 8 ms 输入合并窗口。
本次只改名称引擎，不涉及正文、模型或 UI 绘制。本机合成百万条目热缓存结果不代表其它机器。

普通首段 p95 改善约 **2.3 倍**，批量更新期间约 **2.5 倍**，连续输入持平。
百万索引本轮测试峰值约 **122–132 MiB**，比上一版约 206 MiB 降低约 **36–41%**，
回到此前 150 MiB 名称引擎目标以内。这不是所有文件名分布、长期修改或全库重写下的内存上限。
当前结论仅涉及引擎和 IPC，不是 Tinycast/Spotlight 完整 UI 对比。

单文件新增/改名/修改/删除各 30 次，p95 从 **30.51 / 30.51 / 30.11 / 27.94 ms**
变为 **26.46 / 26.45 / 26.51 / 25.81 ms**。离线变更恢复约 **468 → 490 ms**。
60 秒空闲 CPU 约 **0.28% → 0.30% 单核**，采样期间没有运行构建或其它本任务性能测试。
增量测试末尾 100 次重复查询曾出现新版本 p95 1.78 ms、旧版本 1.35 ms；
随后在同一增量后数据库上预热，按旧/新/新/旧顺序各测 1000 次，p95 分别
**1.163 / 1.180 / 1.150 / 1.172 ms**，没有复现持续退化。两份原始记录均保留。

真实 OneDrive 名称索引另做 55 条查询对照，结果与排序全部一致，socket p95
约 **0.483 → 0.380 ms**；这是小资料库测量，不计 GUI 绘制。

## 实现

`Paged<T>` 用 `Arc` 共享元数据块（4096 条）和名称字节块（64 KiB），
写入时仅复制发生变化的块；同一字符串不跨字节块。查询线程持有已提交的不可变快照，
写入线程独占自己的快照，完成 SQLite 事务后发布共享快照。
通道容量仍为 1。接收方直接切换快照，不再逐条重放变更记录，后续版本继续共享未变块。
旧快照仍被读取时不会被修改，失败的 SQLite 事务不会发布。
`index_allocated_bytes` 仍是单份逻辑快照的数据块容量，不能把两个快照相加当作物理内存；
报告的内存使用整个服务进程的 physical footprint，包括共享页、查询缓冲和写入线程。

每条记录增加 8 字节相邻字节签名，包含规范化名称、全拼和首字母键。
查询必需位缺失时可立即跳过该记录；位碰撞只增加候选，最终仍由原有匹配器验证和排序。
它不截断候选、不改变匹配含义；单 ASCII 字符没有相邻字节，直接保留完整匹配路径。
查询仍为 O(N)，没有声称已经实现倒排检索；高命中、路径与连续输入缓存分别验证。

SQLite v2 格式未变，现有数据库无需重建。签名与内存块在恢复时创建。
本轮单次百万恢复到 socket 可答约 443 → 477 ms；另一次顺序复测存在更大的调度波动，
这不是冷磁盘或严格启动速度改善的证据。原有历史无效时启动扫描、长时间重命名产生
名称池旧内容、慢客户端读取超时等边界仍存在。

## 验证口径与复现

- 真实百万文件/目录合成树和同一份 SQLite 的独立副本；同一台机器、同一查询顺序。
- 普通首段每次先用空查询清除连续输入缓存。50 条普通查询、5 条高命中、1 条路径，
  各 20 次，共 **1120 / 1120** 返回结果、分数及命中类型与基线一致。
- 连续输入另测 **440 / 440** 查询结果与排序一致。
- 批量测试每次搬入 10,000 空文件，持续查询既有和新增名称，移走后确认删除。
  每个版本 30 批次，两种顺序各跑一轮；结束时恢复 1,000,000 条目。
  查询样本数随每个窗口内完成请求数而变化，两个版本不是固定相同样本数；所有慢样本保留。
- 初期 10 批次探索中双方均出现过可见性慢样本（新约 195 ms、旧约 367 ms），
  没有因单次最大值宣布改善。之后扩大为 30 批次并交换顺序，报告完整分布与最大值。
- 分块共享和签名单独试验过：仅分块显著省内存但查询略退化；签名及路径遍历调整后才保留。
  移除匹配器的预检查反而变慢，未纳入最终版本。
- Rust 3 个单元测试、6 个集成测试、fmt 和严格 clippy 通过；覆盖跨块、中文/NFC/NFD、
  拼音与三种模式、快照重命名/删除隔离、缓存、FSEvents、离线恢复和单写入者。
