## 建议

名称搜索已具备进入内容阶段的性能基础，不必继续为零点几毫秒无限优化。
下一步先打通小规模正文提取、中文全文与语义检索，再扩展容量；名称通道保持独立。
更新：独立文本推理及合成查询已测试，见 [后端报告](inference-backends.md)；真实资料库语义找回率仍待测量。

本地路线使用 **EmbeddingGemma 2**（`google/embeddinggemma-2`）。
它与云端 **Gemini Embedding 2**（Gemini API `gemini-embedding-2`）是不同产品。
官方支持 EmbeddingGemma 2 文本模式单独加载约 270M 参数、原生 768 维及 256 等截短维度；
截短后需重新归一化，不能把不同维度混用。参数量不是进程实际内存。
参考：[本地模型卡](https://ai.google.dev/gemma/docs/embeddinggemma/model_card_2)、
[官方本地推理示例](https://ai.google.dev/gemma/docs/embeddinggemma/inference-embeddinggemma-with-sentence-transformers)、
[Gemini API 模型](https://ai.google.dev/gemini-api/docs/models/gemini-embedding-2)。

## 可选配置与体验

以下只是拟议配置，不会修改当前用户设置：

```json
{
  "content": { "enabled": false, "roots": [], "formats": ["txt", "md", "pdf", "docx"] },
  "semantic": { "enabled": false, "model": "google/embeddinggemma-2", "dimensions": 768 },
  "model": { "idle_release_seconds": 30 }
}
```

- 默认保持名称搜索。开启内容能力时选择正文范围，不能沿用名称索引目录就自动读全部文件。
- 语义依赖内容；可只开全文而不开模型。关掉语义就停止向量任务、取消其查询并释放模型。
- 关闭保留已建内容索引，另提供清理；暂停后台构建时可以搜索既有结果并显示其更新状态。
- 只处理已经下载的文件。OneDrive 占位文件显示未建立内容索引，不自动触发下载。
- 主搜索先按现有 8 ms 合并窗口发布名称结果；输入稳定约 150 ms 后补充语义结果。
  保留当前选中项，不让晚到结果改变 Enter 将打开的文件；中文组字期间不发半成品请求。
- 模型缺失、加载慢或推理失败只影响语义，名称/全文照常工作；不自动切换云端 API。

## 最短实现路径

1. **先验证可检索的正文**：从明确授权的小资料集开始，先 TXT/MD，再 PDF 文本层、DOCX 段落和表格。
   Rust 管理 file ID、内容 generation、任务和 SQLite；Swift helper 处理 PDFKit/Cocoa。
   原文片段保留页码或段落定位，不给 DOCX 虚构页码。不支持扫描 PDF OCR、媒体和问答。
2. **建立全文基线**：沿用技术方案的中文相邻双字键 + 原文验证，返回片段与位置。
   名称、正文任务分别排队；每个文档失败不阻塞其他文件。先确认中文中间词可搜，再接模型。
3. **接一个独立模型 worker**：复用固定版本 DigUp 的 MIT `LlamaEmbedder`、worker 通信及
   llama.cpp/Metal 构建思路，不移植完整应用。Rust 通过独立本地通道调度模型，
   名称 socket 线程不执行解析、推理或等待 GPU；后台构建按短批次让出资源，查询优先。
4. **小范围比较 768 与 256 维**：先以 768 维建立正确性基线，实测中文查询后再决定是否默认 256。
   10 万片段 FP16 向量缓冲分别约 146.5 / 48.8 MiB；这只是存储计算，未包含模型和工作区。
   先用精确向量检索，扫描真成为瓶颈再引入 ANN。全文/语义用 RRF 融合并按文件去重，
   名称精确命中保持优先。相似度不显示为“正确率”。
5. **最后接 Tinycast 开关和结果展示**：沿用独立引擎；Raycast 标准扩展调用同一个服务，
   不承诺向原版 Raycast 主搜索框注入结果。能力开关与正文范围授权分别存储，配置导入不能自动授权读正文。

本机参考源码：DigUp `6faa29e`。其文本 Q8_0 GGUF 清单固定 revision 为
`bfcd298762cc34d0357ece5ebdd31791a3a374d8`，约 310 MB；后续已下载并验证文件，已完成独立推理实验，尚未接入搜索。
`textOnly` 目前同时把 token 预算设为 512，复用时必须拆开“只加载文本权重”与 token 预算，
避免把文档静默截成查询长度。保留 tokenizer 限额，按段落分块，首版文档含提示最多 2048 tokens。
官方参考推理使用 BF16/FP32，不能直接用 F16 推理；向量落盘量化另行测质量。
以上模型约束依据模型卡，DigUp 路径和固定版本依据已读的本地源码。

## 通过什么才进入日常体验

- 公共/合成小语料先跑通提取→全文→向量→打开原文，再用明确授权的真实目录验证。
- 留出至少 50 条有答案查询（中文至少 30 条）与 20 条无答案查询；按既有
  [验收目标](performance-acceptance.md) 检查 Hit@5、MRR@10 和错误接受率。
- 同时测名称首段/连续输入、内容更新期间名称查询、模型冷热请求和全部进程 physical footprint。
  名称 p95 若较当前基线持续恶化超过 10%，先缩小后台批次/降低并行度，不直接发布。
- 内容反复修改、删除、重命名时核对 generation；旧任务不得把已删除或过期的片段写回。
- 关闭语义无需安装模型仍可运行名称/全文；30 秒空闲释放模型。本机热语义 p95 ≤ 300 ms、
  10 万片段额外内存 ≤ 1 GiB 是目标，尚不是承诺或实测结果。

下一次实施建议先完成步骤 1–3 的小语料端到端验证，随后决定模型默认维度和资料库范围。
